# Known Issues

## 55. mp4を遮断すると `#loadingOverlay` が残り、「測れているのに何も見えていない」スクショになる（2026-08-26）

KNOWN_ISSUES 49 で mp4 を `Network.setBlockedURLs` で遮断すると、**`window.load` が発火しなくなる**。
`index.html` の冒頭にある `<div class="loading-overlay" id="loadingOverlay">` は load で消える作りなので、
**遮断した状態では永久に画面を覆ったまま**になる。

厄介なのは**DOMの計測は全部成功する**こと。今回、代表スライドの
`box=610x430 / naturalWidth=1500x2000 / 横溢れ0` が正常に取れているのに、
撮れたPNGは**ロゴだけのローディング画面**だった（14KBという不自然な小ささが唯一の手がかり）。
数値だけ見て合格にしていたら、公開報告に「目視した」と嘘を書くところだった。

- **対策**: スクショ直前に `document.getElementById('loadingOverlay')?.remove()` を実行する
- **一般化**: 遮断・スタブ・モックで「読み込み完了イベント」を殺すと、
  それに紐づくUIの後始末も同時に殺される。**計測の成功はスクショの成功を意味しない**
- メモリ「UI検証はスクショまで」の具体例。**PNGのファイルサイズが不自然に小さい時は中身を必ず開く**

## 54. `loading="lazy"` の画像は画面外だと `naturalWidth=0`。欠損判定もすり抜ける（2026-08-26）

`profile.html` の `.ph-profile-photo` は `loading="lazy"`。**ビューポートに入るまで読み込まれない**ため、
スクロール前に測ると `naturalWidth=0` を返す。これは「画像が壊れている」場合と**同じ値**である。

さらに、よく使う欠損判定 `[...document.images].filter(i => i.complete && i.naturalWidth === 0)` は、
未読み込みの lazy 画像では `complete === false` なので**カウントされない**。
つまり `broken=0` かつ `naturalWidth=0` という、一見矛盾した結果が出る。

- **対策**: 測る前に `el.scrollIntoView({block:'center'})` → **`naturalWidth > 0` になるまでポーリング**（上限20秒）
- 同じ画面でも**実行ごとに揺れる**（今回はPC1280だけ0x0、次の実行では390だけ0x0）。
  1回の成功で確定させず、**全ケースが同時に緑になる実行を1本作る**こと
- 待たずに測って「画像が壊れている」と報告すると、直す必要のないものを直しに行くことになる

## 53. 「PC操作の順番を次のセッションへ明け渡した」中断は障害ではない（2026-08-26）

セッションが `PC操作の順番を次のセッションへ明け渡したため、このターンを中断しました` で
終わることがある。**これはネットワーク断でもツールの失敗でもなく、デスクトップ操作の
排他ロックを別セッションへ譲った正常な動作**である。原因調査に時間を使う必要はない。

- **やること**: 再開時に `git status` と `/api/messages` の実体を先に見て、
  **中断地点の直前の作業から続ける**。中断＝未完了とは限らない
  （並行セッションが先に片付けていることがある）
- **予防**: PC操作（LINE送信・実画面キャプチャ）を要する工程は**ターンの最後にまとめる**。
  ファイル編集・ヘッドレス検証・docs更新のような**ロック不要の作業を先に片付けておく**と、
  途中で明け渡しても失われる作業が無い。今回はこの順で進めて取りこぼしゼロだった
- `/api/messages` のようなHTTP経路の確認は、PC操作の順番と無関係に通る

## 52. EXIF Orientation の付いた写真は Read ツールで「横倒し」に見える（2026-08-26）

代表写真の差し替えで、旧 `images/IMG_4347.JPG` を Read すると**横位置（4032×3024・4:3）**に見え、
`theme/subpage.css` にも「4032x3024（4:3 横位置）。縦長に切ると人物が切れる」と
**誤った前提のコメントが書かれていた**。実際は **EXIF Orientation=6** で、
**ブラウザ上は縦位置 3:4 で表示されていた**。

**Read ツールと `sips -g pixelWidth/pixelHeight` は EXIF の回転を無視する。**
この2つだけを見て `aspect-ratio` や `object-fit` を決めると、比率が90度ずれる。

```bash
/usr/bin/sips -g pixelWidth -g pixelHeight -g format img.jpg   # 回転前の生の値
mdls -name kMDItemOrientation img.jpg                          # 0=横 / 1=縦（回転あり）
```

**確実なのはブラウザに実際に描かせて `naturalWidth` / `naturalHeight` を読むこと。**
CDP で `img.naturalWidth` を取れば、ブラウザが EXIF を適用した後の値が返る
（今回 `1500x2000` を確認してから `aspect-ratio: 3/4` を確定した）。

**新しく置く写真は EXIF 回転に依存しない向き（＝ピクセルの並びどおり）で保存する。**
今回の `morishita-daihyo.jpg` は 1500×2000 の素直な縦位置で、回転指定を持たない。

### 横長の枠へ縦写真を `cover` で入れるときの頭上余白

`#instructor-image-container .slide-img` は横長枠。3:4 の縦写真を `object-fit: cover` で
入れると上下が大きく切れるため、`object-position` の**縦位置で顔の高さを決める**。

- `center 20%` … 頭頂が枠の上辺に接して**窮屈に見える**（実測・却下）
- **`center 8%`** … 頭上に余白が残る（PC 1440・スマホ 390 の両方で目視確認して採用）

この規則は**代表写真のコンテナ限定**なので、他のスライド画像には影響しない。

## 51. お客様へ投げた質問は、別ルートで答えが来ても必ず閉じに行く（2026-08-25）

12:37、森下様へ料金表バグの修正報告を送り、末尾をこう締めた。

> 本番サイトへの公開は自動では行わない設定のため、公開してよろしければ「公開して」とお伝えください。🍊

その4分後、**Human Ownerが（森下様ではなく）「公開して」と指示**し、
実際には 12:41 の自動コミット `b5b30b3` で公開が完了した。
ところが**森下様には何も届かないまま**で、13:21に当方が報告するまでの**44分間**、
森下様は「自分が返事をしないと公開されない」と思って待たれていた状態だった。

**危険なのは、こちらの帳簿上は「完了」に見えること。** git は公開済み、docs も「完了」、
公開の実測検証まで済んでいる。**欠けているのは相手の認識だけ**なので、内部の確認では絶対に出てこない。

### 判定のしかた

送信済みメッセージの**末尾**を見て、次のいずれかで終わっていたら**未完了として扱う**。

- 「〜とお伝えください」「〜であればお知らせください」「ご希望があれば」
- 「ご確認をお願いします」「どちらがよろしいでしょうか」

そのうえで、**その問いの答えが別ルート（Human Owner・自動処理・他セッション）で
既に出ていないか**を確認する。出ていれば、相手へ閉じる連絡を送るまでが1件である。

### 報告文の書き方でも予防できる

自動コミット・自動デプロイが動く運用では、「公開は自動では行いません」と書いた直後に
自動で公開されることが実際に起きる（KNOWN_ISSUES 38 の4度の再発と同じ構造）。
**確定していない段取りをお客様へ約束として書かない。**
「公開まで完了しましたらあらためてご連絡します」のように、
**こちらが動く側**の書き方にしておけば、誰が引き金を引いても報告義務が残る。

関連: 38（文書と実体の食い違い）、39（「新着なし」は当てにならない）。
いずれも**内部の記録ではなく、相手側から見た状態を一次情報として確認する**という同じ原則。

## 50. 料金表のクリック検証は「HTMLの出現」を合図にしてはいけない（2026-08-25）

ヘッドレスで `[data-tab-link="hojin"]` の**存在**を待って 1.5 秒後にクリックしたところ、
`scrollY=0` / `activeTab=tab-kojin` のまま**何も起きなかった**。バグが直っていないように見えるが、
実際は **`pricing.js` がまだ読み込まれておらずリスナーが張られていなかった**だけだった。

`ComponentLoader` は HTML を差し込んでから JS を後追いで読む（`?v=' + Date.now()`）。
本番では実測で **約4秒**かかる。HTML の出現とリスナー装着の間にこの空白がある。

**正しい待ち方** — タブボタンを実際に押して、切り替わることでリスナー装着を確認してから計測に入る:

```js
for (let i = 0; i < 120; i++) {
  await sleep(500);
  const ok = await evaluate(`(() => {
    const b = document.querySelector('.tab-btn[data-tab="hojin"]');
    if (!b) return false;
    b.click();
    return (document.querySelector('.tab-content.active')||{}).id === 'tab-hojin';
  })()`);
  if (ok) break;
}
// 個人タブ・最上部へ戻してから本番の計測を始める
```

この空振りを「修正が効いていない」と読み違えると、直っているものを再修正しに行く。

## 44. 「反映されていない」の申告は、まずLINEプレビューと端末キャッシュを疑う（2026-08-21）

森下様からお電話で「何かの作業がホームページに反映されていない」とのご指摘があったが、
**調査の結果、本番サイトは全項目反映済み**（16ファイルbyte一致・修正8項目すべて実測確認）だった。

最有力の原因は **LINEのリンクプレビュー**。9:37に送った完了報告のカードに、
森下様が削除をご依頼された「記帳代行だけの依頼」が**そのまま表示されていた**。
実体は削除済みで、LINEが 01:44 に取得したOGPのキャッシュである（42 参照）。

**「削除しました」と書いたメッセージの中に、消したはずの語が並んで表示される。**
相手からは「言っていることと画面が違う」に見え、こちらの報告全体の信頼を落とす。

### 切り分けの順番

1. `curl` + `diff` で配信物とローカルの一致を確認（38）— ここが一致すればサイトは正しい
2. ご依頼された文言を本番HTMLで直接 `grep -c` する（0件であることを数える）
3. 実画面のスクリーンショットを撮る（37 / 41 の手順。目視まで行う）
4. そのうえで **LINEのプレビュー / 端末のキャッシュ / Google検索のスニペット** を疑う

### 予防

- **修正後にURLを送り直すときは、プレビューが古い可能性がある旨を一言添える。**
  2026-08-21 の判断（42・DECISIONS）は「訂正メッセージは送らない」だったが、
  **何も言わないと相手が先に気づいて不信になる**ことが今回実証された。
  「LINEのカードの説明文は少し前の内容が出ることがあります」の1行で足りる
- サイトのURLを送るときは、**LINEのカードからではなくブラウザで開いていただく**よう促す
  （LINE内蔵ブラウザは独自にページを保持することがある。サーバー側は
  `cache-control: public, max-age=0, must-revalidate` を返しており、サーバーの問題ではない）

### 本番HTMLをiframeへ入れて撮るときの追加の罠（41 の続き）

`--dump-dom` で取ったトップページのDOMを保存して撮り直すと、**ComponentLoaderのJSが
再実行されてフッターを作り直そうとし、`file://` からのfetchがCORSで失敗して消える**。
`.footer-sitemap` が「あるときと無いとき」がある、という不安定な挙動になる。

```bash
# 保存したDOMから <script> を全部落としてから撮る
python3 -c "import re,sys;h=open('_t.html').read();open('_t2.html','w').write(re.sub(r'<script\b.*?</script>','',h,flags=re.S|re.I))"
```

また **iframeを数万pxの高さにして負のオフセットで撮る方法は、
ビューポートから遠すぎる領域が描画されず真っ黒/単色のPNGになる**ことがある
（今回 top:-64930px で発生。PNGが5KB以下なら描画失敗を疑う）。
その場合は対象要素のマークアップとCSSだけを抜き出した小さなページにして撮るほうが確実。

## 42. LINEのリンクプレビューは古い。公開内容の証拠に使ってはいけない（2026-08-21）

`2026-08-21 01:44` の記録では、LINEが生成したリンクプレビューに各ページのタイトルと説明文が
出たことを「公開状態とメタ情報が正しいことの独立した確認」として扱っていた。

```bash
grep -o '<meta name="description" content="[^"]*"' faq.html          # 当該語なし
```

## 41. `file://` のiframe計測が空振りする真因は `--allow-file-access-from-files` の欠落（2026-08-21）

`contentWindow.scrollTo()` は `--screenshot` に**正しく反映された**（実測確認済み）。

**教訓**: iframe を触るJSは `try/catch` で囲み、`catch` の中身を `document.title` などへ

先頭に `RESULT ` のような固定マーカーを付けて `grep -o 'RESULT {.*}'` で取り出すと確実。

### スクロールが使えない事情があるなら負のオフセットでも撮れる

```html

</div>
```

## 38. 引き継ぎ資料の「本番反映は未実施」は当てにならない。pushの前に必ず実体を見る（2026-08-21）

文書は「まだpushしていない」時点の記述で固まり、その直後のコミット／反映で古くなる。

**pushの前に必ずこの3つを実行する。**

```bash
git rev-parse HEAD                       # ローカル
git ls-remote origin main                # リモート（この2つが一致していれば push 済み）
git rev-list --left-right --count origin/main...main   # 0<TAB>0 なら差分なし
```

さらに「本番に出ているか」は remote の SHA では確定しない（デプロイの遅延・失敗がある）。
**配信物とローカルを byte で突き合わせる**のが唯一確実な確認方法。

```bash
for f in index.html faq.html profile.html theme/subpage.css sitemap.xml; do
  curl -s "https://www.morishita-tax.jp/$f" -o /tmp/_p.tmp
  diff -q /tmp/_p.tmp "$f" >/dev/null 2>&1 && echo "$f MATCH" || echo "$f DIFFERS"
done
```

「未反映と書いてあるから push する」ではなく、**差分が無ければ「既に公開済み」と報告する**。
KNOWN_ISSUES 11（未pushの取りこぼし）と対になる、逆方向の食い違いである。

- A2E は「1フレームだけ直す」ができず、**微調整でも1本分（Seedance 2.0 で 2460 コイン）を消費する**
- したがって動画の不具合報告を受けたら、**まず `ffmpeg` のカット・トリム・クロップで
  消せないかを検討する**。消せるなら受付停止（16）の対象外として即日対応できる
- 実際に 20 のバグはこの方法で解消し、**コイン消費 0** で本番反映した（v6）

**継ぎ目の作り方（実測した結論）**

- **ハードカットを第一候補にする。** xfade の crossfade は、消えゆく前カットの人物と
  次カットの人物が重なって**「人が2人いる」ように見える**（1-m と同系統。森下様が過去に指摘済み）
- 0.30 / 0.20 / 0.125 秒のいずれでもゴーストは出た。フェード長を短くしても消えない
- カット後は必ず**先頭フレームと末尾フレームの輝度差**を測り、原版と同等かを確認する

```bash
# 該当区間を落としてハードカットで繋ぐ（音声なしのループ動画の場合）
ffmpeg -i in.mp4 -filter_complex \
  "[0:v]fps=24,split=2[s0][s1];\
   [s0]trim=start=0:end=<切り始め>,setpts=PTS-STARTPTS[a];\
   [s1]trim=start=<切り終わり>,setpts=PTS-STARTPTS[b];\
   [a][b]concat=n=2:v=1:a=0,format=yuv420p[v]" \
  -map "[v]" -an -c:v libx264 -profile:v high -level 4.0 -r 24 -crf 20 -preset slow \
  -movflags +faststart -y out.mp4

# ループ継ぎ目の検証（原版と同じ値なら劣化なし）
n=$(ffprobe -v error -count_frames -select_streams v:0 -show_entries stream=nb_read_frames -of csv=p=0 out.mp4)
ffmpeg -v error -i out.mp4 -vf "select=eq(n\,0),scale=640:-1"        -frames:v 1 -y /tmp/_f0.png
ffmpeg -v error -i out.mp4 -vf "select=eq(n\,$((n-1))),scale=640:-1" -frames:v 1 -y /tmp/_fl.png
ffmpeg -i /tmp/_f0.png -i /tmp/_fl.png -filter_complex \
  "[0][1]blend=all_mode=difference,signalstats,metadata=print:key=lavfi.signalstats.YAVG" -f null -
```

`trim` の前後に `fps=24` を入れないと `xfade` が
`The inputs needs to be a constant frame rate` で失敗する。`concat` でも入れておくのが安全。

### 9-b. ヘッドレス Chrome は幅 500px 未満のウィンドウを作れない
